JavaScript - Parte I

Questi appunti coprono la Parte I della lezione su JavaScript: come si include il linguaggio in una pagina web, come si dichiarano le variabili, come funzionano funzioni e oggetti. Moduli, asincronia e manipolazione del DOM arriveranno nelle lezioni successive.

Sono pensati per chi arriva da Java: conosci già variabili, cicli, funzioni e oggetti, ma non hai mai scritto una riga di JavaScript. Questo è esattamente il punto di partenza giusto, perché JavaScript assomiglia a Java solo in superficie. La sintassi dei cicli e degli if è praticamente identica, quindi ti sembrerà tutto familiare — ma sotto ci sono differenze profonde che, se non le conosci, ti faranno sembrare il codice "rotto" senza capire perché.

Per questo motivo, ogni volta che una cosa funziona diversamente da come ti aspetteresti, lo troverai scritto esplicitamente.

0. Da Java a JavaScript: cosa cambia davvero

Prima di entrare nel dettaglio, conviene mettere sul tavolo le differenze strutturali. Se tieni a mente questa tabella, il resto della lezione risulterà molto più prevedibile.

Dove vive il codice Classe con public static void main Sequenza di istruzioni in un file .js, oppure dentro <script>
Compilazione Compilato in bytecode, errori a compile-time Interpretato dal motore JS, errori (per lo più) a runtime

Oggetti Si creano solo istanziando una classe Si creano "a mano" con {} — la classe è opzionale

Il filo conduttore è uno solo: Java è rigido e ti protegge dagli errori; JavaScript è permissivo e si fida di te. Quasi tutto ciò che in Java è un errore di compilazione, in JavaScript o è silenziosamente legale o esplode a runtime quando meno te lo aspetti.

1. Perché esiste JavaScript

Il problema che risolve

Con HTML definiamo la struttura di una pagina e con CSS il suo aspetto — ma una pagina HTML da sola è statica. Una volta che il server ci ha mandato l'HTML, quel contenuto non cambia più: resta identico finché non ricarichi la pagina. Non c'è modo, con i soli HTML e CSS, di far comparire un messaggio dopo che l'utente clicca un bottone, o di validare un form mentre lo si compila.

JavaScript nasce esattamente per colmare questa lacuna: è il linguaggio che viene eseguito dentro il browser e che permette alla pagina di reagire — di cambiare mentre la stai guardando. Questa è la differenza concettuale più importante da fissare: HTML e CSS descrivono, JavaScript esegue.

Cos'è, tecnicamente

  • È un linguaggio ad alto livello, debolmente tipizzato (loosely-typed) e di scripting.
  • È stato introdotto dal browser Netscape nel 1995.
  • È stato progettato per essere incluso nelle pagine web ed eseguito all'interno del browser, con l'obiettivo di rendere i documenti HTML più dinamici.
  • I programmi JavaScript (detti script) sono interpretati come testo semplice dal JS Engine, il motore JavaScript del browser.

Il termine "debolmente tipizzato" merita una precisazione, perché è il cuore della differenza con Java. In Java scrivi int x = 5; e da quel momento x è un intero per sempre: se provi ad assegnargli "ciao", il compilatore ti ferma. In JavaScript scrivi let x = 5; e x è semplicemente "la scatola in cui ho messo 5". Nulla vieta, due righe dopo, di scrivere x = "ciao" e poi x = false. La variabile non ha un tipo: ce l'ha il valore che contiene in quel momento.

Perché è importante: in Java il compilatore è il tuo primo revisore di codice. In JavaScript quel revisore non esiste. Molti errori che in Java scopri mentre scrivi, qui li scopri quando l'utente sta già usando la pagina. È il motivo per cui più avanti troverai così tanti avvertimenti sulla disciplina da tenere.

JavaScript oggi

Vale la pena sapere che JavaScript ha da tempo superato i confini del browser. Oggi viene usato anche per software backend, applicazioni desktop e mobile, e scripting generico. È il linguaggio di programmazione più popolare al mondo: nel 2023 era usato dal 66% degli sviluppatori professionisti secondo il sondaggio StackOverflow.

Tecnicamente, JavaScript implementa la specifica ECMAScript, lo standard mantenuto da ECMA International. È per questo che nei nomi delle versioni sentirai parlare di "ECMAScript 5", "ECMAScript 6" o "ES6": è il nome dello standard, mentre "JavaScript" è il nome del linguaggio che lo implementa.

2. Includere JavaScript in una Pagina Web

Prima ancora di scrivere codice, serve capire dove va messo. Esistono due modi, e vale la pena conoscerli entrambi perché li incontrerai entrambi.

JavaScript interno

Il codice viene scritto direttamente nella pagina, dentro un elemento <script>, che puoi mettere nel <head> oppure nel <body>:

<script>
  console.log("Hello World!");
</script>

Il tag <script> è l'equivalente, per JavaScript, di quello che in Java sarebbe il main: è il punto in cui il motore del browser capisce "da qui in poi c'è codice da eseguire". La funzione console.log() è invece il tuo System.out.println(): serve a stampare qualcosa sulla console del browser (la apri con F12 → Console). La useremo in tutti gli esempi.

JavaScript esterno

In alternativa, il codice sta in un file separato con estensione .js, e viene collegato tramite l'attributo src:

<script src="script.js"></script>

Questo è il modo che si usa nella pratica, per la stessa ragione per cui in Java non scrivi tutto in un unico file: separare responsabilità e poter riusare il codice. Da qui in avanti, quando negli esempi vedrai solo il codice JavaScript "nudo", immagina che sia contenuto in uno di questi due posti.

Nota: l'estensione .js non è una convenzione facoltativa — è richiesta.

Esempio completo: Hello World

Mettendo insieme i pezzi, una pagina HTML con JavaScript interno appare così:

<!DOCTYPE html>
<html>
  <head>
    <meta charset="utf-8" />
    <title>JavaScript</title>
    <script>
      console.log("Hello World!");
    </script>
  </head>
  <body>
    <h1>Hello!</h1>
  </body>
</html>

Nota una cosa: lo <script> sta nel <head>, quindi il codice viene eseguito prima che il <body> venga costruito. Per ora non è un problema (stampiamo solo su console), ma tienilo a mente: quando in futuro il codice dovrà manipolare elementi della pagina, il momento in cui lo script viene eseguito diventerà cruciale.

3. "use strict": la modalità moderna

Qui c'è una particolarità di JavaScript che in Java non ha alcun equivalente, e che è importante capire subito perché condizionerà tutti gli esempi del corso.

Per molto tempo JavaScript si è evoluto senza rompere la compatibilità: venivano aggiunte nuove funzionalità, ma quelle esistenti non venivano mai toccate. Questo garantiva che le vecchie pagine continuassero a funzionare — ma aveva un costo: il linguaggio non poteva correggere i propri difetti storici.

Nel 2009 arrivò ECMAScript 5 (ES5), che per la prima volta modificò alcune funzionalità esistenti. Per non rompere i siti già esistenti, questi cambiamenti furono resi disattivati di default, e attivabili volontariamente tramite la direttiva "use strict" da mettere nella prima riga dello script:

"use strict";
/* JavaScript code here */

Quando questa direttiva è attiva, il motore JavaScript applica regole più severe — rifiuta codice sciatto che altrimenti accetterebbe, e trasforma in errori alcune operazioni che in modalità normale passerebbero silenziosamente. È un po' come se, dopo anni di "fai quello che vuoi", il linguaggio ti offrisse un interruttore per dire "ok, ora avvertimi se sbaglio".

⚠️ Attenzione: nel corso, salvo indicazione contraria, faremo riferimento alla versione moderna e "strict" di JavaScript. Assicurati di dichiarare "use strict" in cima ai tuoi script, altrimenti il comportamento di alcuni esempi non corrisponderà a quanto descritto.

4. Il Linguaggio: gli Statement

JavaScript supporta i paradigmi imperativo, funzionale e orientato agli oggetti — quindi la tua esperienza Java non va buttata: la parte imperativa (variabili, cicli, condizionali) la ritroverai quasi identica. In più, come vedremo, c'è una forte componente funzionale che in Java esiste solo in forma limitata (le lambda e gli stream).

Un programma JavaScript è una sequenza di statement (istruzioni), composti da valori, operatori, espressioni, keyword e commenti. Nota l'assenza di un involucro: non esiste una classe, non esiste un public static void main. Il file è semplicemente una lista di istruzioni che vengono eseguite dall'alto verso il basso.

La sintassi è simile a Java e C, ma molto più permissiva. La differenza più evidente riguarda come si separano le istruzioni: in Java ogni istruzione deve finire con ;. In JavaScript i punto e virgola sono opzionali, perché gli a capo bastano a delimitare un'istruzione:

//con i punti e virgola
msg = "Hello";
num = 1;
console.log(msg);

//senza punti e virgola
msg = "Hello"
num = 1
console.log(msg)

/* statement sulla stessa riga
   (e commento multi-linea) */
msg="Hello"; num=1; console.log(msg);

Come vedi, i commenti funzionano esattamente come in Java: // per la riga singola, /* ... */ per il blocco. E come in Java, gli a capo non contano nulla per il linguaggio: puoi mettere tre istruzioni sulla stessa riga e funziona lo stesso.

Buona pratica: anche se sono opzionali, delimitare gli statement con il punto e virgola è preferibile. Il motivo è che JavaScript, in alcuni casi limite, indovina male dove finisce un'istruzione e ne combina due insieme, generando comportamenti difficili da diagnosticare. Scrivere sempre ; elimina il problema alla radice. In questi appunti, quando il codice proviene dalle slide, troverai a volte l'uno a volte l'altro stile — è intenzionale, per mostrarti che entrambi sono validi.

5. Variabili e Scope

Questa è la sezione più importante della lezione, e anche quella in cui chi arriva da Java rischia più confusione. Il motivo è che la maggior parte dei linguaggi non ha il concetto di hoisting, e JavaScript ce l'ha — con regole diverse a seconda di come dichiari la variabile.

Vale quindi la pena procedere con ordine: prima come si dichiara una variabile, poi dove quella variabile esiste (lo scope), e infine quando diventa utilizzabile (l'hoisting).

5.1 Il ciclo di vita di una variabile

Dichiarare una variabile in JavaScript, contrariamente a quanto si potrebbe pensare, consiste di tre fasi distinte:

  1. Dichiarazione (declaration): il nome della variabile viene legato allo scope corrente. Da questo momento il motore sa che "esiste una cosa chiamata x qui dentro".
  2. Inizializzazione (initialization): alla variabile viene assegnato un valore.
  3. Utilizzo (usage): la variabile può finalmente essere referenziata per leggerne il valore.

In Java queste tre fasi tendono a coincidere in una sola riga (int x = 5; fa tutto insieme), e per questo non ci si pensa mai. In JavaScript si separano, e la separazione ha conseguenze pratiche molto concrete:

      Dichiarazione              Inizializzazione               Utilizzo
   (binding nello scope)      (assegnazione del valore)    (lettura del valore)
             |                           |                          |
             v                           v                          v
   ----------+---------------------------+--------------------------+--------> tempo
             |<---- Temporal Dead Zone (TDZ) ---->|
             |                                    |
    variabile inaccessibile            variabile accessibile
    fino all'inizializzazione

La zona tratteggiata nel diagramma ha un nome preciso: Temporal Dead Zone (TDZ). È l'intervallo in cui la variabile esiste già (la dichiarazione è avvenuta) ma non è ancora utilizzabile (l'inizializzazione non è ancora avvenuta). Se provi a leggerla in quel momento, ottieni un errore.

Tieni a mente questo diagramma, perché è la chiave per capire tutto il resto della sezione: hoisting e TDZ sono due facce della stessa medaglia.

5.2 Dichiarare variabili: let e const

Nel JavaScript moderno le variabili si dichiarano con due keyword:

  • let per le variabili "standard", quelle che possono cambiare valore.
  • const per le costanti, che non possono essere riassegnate.
let x;
const y = 42;
console.log(x); //output: undefined
console.log(y); //output: 42

Il primo punto da notare è quello che non c'è: il tipo. In Java scriveresti int x; o final int y = 42;. Qui la keyword non dichiara che tipo di dato conterrà la variabile — dichiara soltanto quanto sarà flessibile. Quindi let assomiglia al int/String/ecc. di Java nel senso che è una variabile riassegnabile, e const assomiglia a final nel senso che è una variabile bloccata.

Il secondo punto è il valore undefined. In Java, una variabile locale dichiarata e non inizializzata non è utilizzabile: il compilatore ti blocca se provi a leggerla. In JavaScript, let x; è perfettamente legale e x vale undefined — un valore speciale che significa "dichiarata, ma nessun valore assegnato". Questo è il primo assaggio della filosofia permissiva del linguaggio: dove Java ti ferma, JavaScript ti dà undefined e va avanti.

5.3 Lo scope: dove una variabile esiste

Prima di parlare di let, const e var, serve sapere dove una variabile vive. JavaScript ha tre livelli di scope:

  • Global Scope: lo scope di tutto il programma.
  • Function Scope: lo scope di una funzione (lo vedremo tra qualche sezione).
  • Module Scope: lo scope di un modulo (lo vedremo nella prossima lezione).

In aggiunta, le variabili dichiarate con let e const possono avere:

  • Block-level scope, ovvero lo scope del blocco più vicino delimitato da una coppia di parentesi graffe {}.

Il block-level scope è quello che ti aspetti da Java: una variabile dichiarata dentro un if, un for o un blocco {} esiste solo lì dentro. Se in Java scrivi:

if (true) {
    int msg = 5;
}
System.out.println(msg); // errore di compilazione

il compilatore si lamenta. In JavaScript con let e const si comporta allo stesso modo — ed è una buona notizia, perché significa che il tuo istinto Java qui funziona. Ma attenzione: questo vale solo per let e const, non per var, come vedremo tra poco.

5.4 let e il block scope

Vediamo la regola in azione:

let bool; //variable declaration
bool = true;
if (bool) {
  //console.log(msg);//msg not accessible here
  let msg = "Hello"; //declaration + assignment
  console.log(msg); //output: Hello
}
//console.log(msg); //msg not defined here
console.log(bool); //output: true

Le due righe commentate sono il punto centrale dell'esempio, e vale la pena leggerle con attenzione:

  • La prima (console.log(msg); dentro l'if, ma prima della dichiarazione) fallirebbe: stiamo cercando di usare msg nella sua TDZ, prima che l'inizializzazione avvenga.
  • La seconda (console.log(msg); fuori dall'if) fallirebbe perché msg è uscita dallo scope: esisteva solo dentro il blocco.

Quindi, riassumendo la regola: le variabili dichiarate con let/const sono confinate al blocco più vicino, e sono accessibili solo dopo che la riga in cui sono dichiarate è stata eseguita. È esattamente il comportamento a cui Java ti ha abituato — con l'unica aggiunta della TDZ, che in Java semplicemente non esiste perché lì il compilatore blocca tutto a monte.

5.5 Hoisting e Temporal Dead Zone

Arriviamo al concetto che non ha nessun equivalente in Java, e che quindi richiede un attimo di pazienza.

Il punto di partenza è questo comportamento del motore JavaScript: prima di eseguire un blocco di codice, il motore lo scansiona e "tira su" (hoists) tutte le dichiarazioni che trova, spostandole virtualmente all'inizio del loro scope. Questa è la definizione di hoisting.

Il problema è che cosa viene tirato su dipende da come hai dichiarato la variabile:

  • Con let e const, solo la dichiarazione viene hoisted all'inizio dello scope, non l'inizializzazione.
  • L'inizializzazione avviene sulla riga in cui originariamente avevi scritto la dichiarazione.

Il risultato è la TDZ: dal punto di vista del motore, la variabile "esiste" fin dall'inizio del blocco (perché la dichiarazione è stata tirata su), ma non è ancora inizializzata fino alla riga originale. In quell'intervallo, leggerla è un errore.

Vediamo l'esempio, che è la rappresentazione più chiara di tutto questo:

// x variable not defined
{
  // Declaration for x is hoisted here
  // TDZ for the x variable
  console.log(x); //raises error
  // TDZ for the x variable
  let x = 1;
  // TDZ ends, x initialized
  // x variable initialized to 1
}
// x variable not defined

L'errore prodotto è:

ReferenceError: can't access lexical declaration 'x' before initialization

Leggiamo i commenti del codice come se fossero una mappa:

{
  // --- INIZIO BLOCCO ---
  // La DICHIARAZIONE di x viene hoisted qui
  // >>> INIZIA LA TDZ DI x <<<
  console.log(x);   // ❌ ReferenceError
  // >>> FINE DELLA TDZ <<<
  let x = 1;        // inizializzazione (avviene QUI, non all'inizio)
  // da questo punto x è utilizzabile
}

Nota la stranezza: la riga console.log(x) viene prima del let x = 1, e in Java una cosa del genere non compilerebbe nemmeno. Qui invece il codice viene eseguito, arriva alla console.log, e solo a runtime scopre che x è nella sua TDZ. Il messaggio d'errore è peraltro molto esplicito ("non puoi accedere a una dichiarazione lessicale prima della sua inizializzazione"), e vale la pena saperlo riconoscere perché è un errore che farai.

Il senso di tutto questo: l'hoisting con TDZ è stato progettato apposta per rendere let/const più sicuri di var. L'idea è: "meglio un errore chiaro subito, che un undefined silenzioso che si propaga per tutto il programma". Tra un attimo vedrai cosa fa var al posto di questo errore, e capirai perché è considerato una cattiva pratica.

5.6 let e lo shadowing

Un'ultima cosa su let, che invece ti sarà familiare: le variabili di un blocco interno possono nascondere (shadowing) variabili omonime di uno scope esterno.

let n; //variable declaration
n = 1;
if (n > 0) {
  let n = 2; //shadows n variable from external scope
  //let n; //error: cannot re-declare in the same block
  console.log(n); //output: 2
}
console.log(n); //output: 1

Il meccanismo è quello che conosci: dentro l'if c'è una nuova variabile n, distinta da quella esterna. Il console.log interno stampa 2 (quella interna), quello esterno stampa 1 (quella esterna, rimasta intatta).

La riga commentata evidenzia l'unica restrizione: non puoi ri-dichiarare la stessa variabile all'interno dello stesso blocco:

let n; //variable declaration
if (n > 0) {
  let n = 2;
  let n = 3; //❌ errore: cannot re-declare in the same block
}

Anche questo è identico a Java, dove due variabili locali con lo stesso nome nello stesso blocco sono un errore di compilazione.

5.7 const

Passiamo a const, che è più semplice perché ha meno sorprese.

  • const dichiara costanti locali con block-level scope.
  • Sono variabili il cui valore non può essere riassegnato.
  • Il comportamento di hoisting è simile a let (quindi: dichiarazione hoisted, TDZ attiva, errore se la usi troppo presto).
const n = 42;
console.log(n); //output: 42
n = 43; //raises a TypeError

Il parallelismo con Java è immediato: const sta a JavaScript come final sta a Java. La differenza è nella natura dell'errore. In Java, riassegnare una variabile final è un errore che scopri compilando. In JavaScript il codice viene eseguito, arriva alla riga n = 43;, e solo a runtime lancia un TypeError.

⚠️ Attenzione — una trappola che riguarda gli oggetti: const impedisce di riassegnare la variabile, non di modificare l'oggetto che essa referenzia. Questo è esattamente il comportamento di final in Java, ma è una sfumatura che inganna spesso. Se scrivi const pet = { name: "Garfield" };, poi pet = {} è vietato, ma pet.name = "Odie" è perfettamente legale. Il motivo è che const blocca il riferimento, non il contenuto. Ci torneremo nella sezione sugli oggetti.

5.8 var: come si faceva prima (e perché non si fa più)

Prima dell'introduzione di ECMAScript 6 nel 2015, le variabili si dichiaravano con la keyword var, oppure implicitamente. Queste modalità esistono ancora e le incontrerai in codice vecchio — ma sono considerate cattiva pratica.

⚠️ A meno che tu non abbia davvero la necessità di supportare browser molto vecchi, non dovresti dichiarare variabili in questi modi: hanno proprietà piuttosto confuse e soggette a errori.

Vediamo il primo esempio, che da solo vale come dimostrazione del problema:

if (true) {
  console.log(n);
  var n = 1;
}
console.log(n);

Prova a indovinare cosa succede. In Java, console.log(n) (la prima riga) sarebbe un errore di compilazione: n non è ancora dichiarata. E il console.log(n) finale sarebbe anch'esso un errore: n è dichiarata dentro l'if, quindi fuori è invisibile.

In JavaScript, nessuno dei due è un errore. Vediamo perché.

5.9 var e l'hoisting "completo"

Ecco la regola che spiega tutto:

  • Le variabili dichiarate con var vengono hoisted allo scope di funzione o globale più vicino — e non hanno alcun block-level scope.
  • E, cosa ancora più insidiosa, vengono anche inizializzate a undefined già all'inizio dello scope.

Rileggi quella seconda riga con attenzione, perché è il punto centrale: con var, non esiste TDZ. Non c'è nessuna fase in cui la variabile è "inaccessibile". Il motore la porta in cima al suo scope e ci mette dentro undefined. Quindi è sempre accessibile — solo che prima della riga di assegnazione contiene undefined.

if (true) {
  console.log(n); //output: undefined
  var n = 1;
}
console.log(n); //output: 1

Ora l'esempio di prima ha senso:

  • Il primo console.log(n) non dà errore: n è stata hoisted a inizio scope e inizializzata a undefined. Stampa undefined.
  • Il secondo console.log(n) non dà errore: nonostante n sia dichiarata dentro un if, var ignora il blocco e la porta allo scope esterno. Stampa 1.

Il secondo esempio mostra la stessa cosa da un altro angolo:

var n;
if (true) {
  console.log(n); //output: undefined
  n = 1;
}
console.log(n); //output: 1

Qui la dichiarazione è esplicita e fuori dal blocco: n esiste dall'inizio, vale undefined, e diventa 1 quando l'if viene eseguito.

Confronto diretto. Immagina di voler usare una variabile prima della sua riga di dichiarazione, dentro un blocco:

Cosa scrivi Cosa ottieni
let n = 1; usata prima ❌ ReferenceError (TDZ) — l'errore ti salva
var n = 1; usata prima ⚠️ undefined — nessun errore, il bug si propaga in silenzio

Ecco perché il corso usa let/const. Non è una questione di stile: var nasconde gli errori, let/const li mostrano.

Riepilogo della sezione:

Aspetto let / const var
Scope Block-level (blocco {} più vicino) Function / Global (nessun block-level)
Hoisting Solo la dichiarazione Dichiarazione + inizializzazione a undefined
Accesso prima della riga ReferenceError (TDZ) undefined (nessun errore)
Ri-dichiarazione Vietata nello stesso blocco Consentita
Da usare? ✅ Sì, sempre ❌ No, solo per codice legacy

5.10 La dichiarazione implicita

C'è un ultimo modo di creare variabili, ed è il peggiore di tutti:

"use strict"
msg = "pls don't do this"  // ReferenceError

Se usi una variabile senza mai dichiararla (nessun let, const o var), JavaScript — in modalità non-strict — crea automaticamente una variabile globale. Questo è pericolosissimo: una variabile globale invisibile, nata da un semplice errore di battitura, che può essere modificata da qualsiasi punto del programma.

È una cattiva pratica, molto soggetta a errori, e non andrebbe mai fatto. È anche vietata nello "strict mode", dove produce un ReferenceError — ed è una delle ragioni principali per cui il corso insiste sull'usare "use strict": quella direttiva trasforma questo errore silenzioso in un errore esplicito.

6. Tipi di Dato Primitivi

Arriviamo alla tipizzazione. Come anticipato, JavaScript è debolmente tipizzato: una stessa variabile può contenere valori di tipo diverso nel tempo. L'operatore typeof ti dice che tipo ha in questo momento il valore contenuto in una variabile.

let x; // variable declared and initialized to undefined
console.log(typeof x); // undefined
x = 42;
console.log(typeof x); // number
x = 3.14;
console.log(typeof x); // number
x = "hello";
console.log(typeof x); // string
x = 'hello';
console.log(typeof x); // string
x = false;
console.log(typeof x); // boolean
x = 10e12;
console.log(typeof x); // number
x = 42 / 0; // Infinity
console.log(typeof x); // number
x = 42 * "Hello"; // NaN
console.log(typeof x); // number

Questo blocco è denso di informazioni, quindi vale la pena leggerlo riga per riga. Nota innanzitutto che x viene riassegnata nove volte con nove tipi diversi, e nessuna di queste assegnazioni produce un errore. In Java questo codice non esisterebbe: una volta dichiarata int x, resterebbe int per sempre.

Poi ci sono quattro cose che in Java non funzionano così:

1. number è un tipo solo. In Java hai int, long, float, double, short, byte — sei tipi numerici distinti, con regole di conversione precise. In JavaScript esiste un unico tipo number, che copre interi (42), decimali (3.14) e notazione esponenziale (10e12). Non devi più chiederti se usare int o double: usi number e basta.

2. Il tipo di una stringa non dipende dalle virgolette. "hello" e 'hello' sono entrambe stringhe, esattamente equivalenti. In Java "hello" è una String e 'hello' sarebbe un char (o un errore, con più caratteri). Qui le due notazioni sono intercambiabili, e in generale la scelta è stilistica.

3. 42 / 0 non lancia un'eccezione. In Java, dividere un intero per zero lancia ArithmeticException. In JavaScript 42 / 0 restituisce Infinity, un valore numerico vero e proprio. Il programma procede, e typeof di Infinity è number. Questo è un esempio perfetto della filosofia del linguaggio: invece di interrompere l'esecuzione con un errore, ti restituisce un valore "strano" e ti lascia andare avanti.

4. NaN è di tipo number. L'ultimo esempio è quello che sorprende di più: 42 * "Hello" — moltiplicare un numero per una stringa, che in Java non compilerebbe nemmeno — produce NaN (Not a Number), e typeof di NaN è... number. È una contraddizione apparente che ha una spiegazione: NaN è il risultato di un'operazione numerica che non ha senso, quindi è categorizzato come numero "non valido". In pratica significa che per verificarlo devi usare una funzione apposita (isNaN()), perché NaN == NaN restituisce false.

Riepilogo dei tipi primitivi:

Valore typeof Note
undefined "undefined" Variabile dichiarata ma non inizializzata
42, 3.14, 10e12 "number" Un unico tipo numerico
Infinity "number" Risultato di 42 / 0
NaN "number" Risultato di operazioni senza senso
"hello", 'hello' "string" Virgolette doppie e singole equivalenti
false / true "boolean"

L'unica aggiunta degna di nota è ** per l'elevamento a potenza, introdotto in ECMAScript 2016. In Java avresti scritto Math.pow(2, 10); in JavaScript puoi scrivere 2 ** 10. Tutto il resto è identico.

7.2 Operatori di confronto

Qui invece comincia la parte delicata. Gli operatori di confronto sono gli stessi di Java, con l'aggiunta di ===:

Operatore Descrizione
== uguale a (equal to)
=== uguale per valore e per tipo (equal value and equal type)
!= diverso (not equal)
!== diverso per valore o per tipo
> maggiore di
< minore di

<= minore o uguale a

Il punto è che in Java hai un solo operatore ==, e sai bene cosa fa: sui tipi primitivi confronta il valore, sugli oggetti confronta la referenza. In JavaScript hai due operatori di uguaglianza che si comportano in modo diverso, e capire la differenza è fondamentale, perché usare quello sbagliato è una delle fonti di bug più comuni.

7.3 L'uguaglianza debole (==)

L'operatore di uguaglianza debole (==) verifica se i suoi due operandi sono uguali. La parola chiave è "debole" perché l'operatore tenta di convertire gli operandi prima di confrontarli, se sono di tipi diversi. Questa conversione automatica si chiama type coercion.

console.log(42 == 42)   //true
console.log("JS" == "JS") //true
console.log("1" == 1)   //true
console.log(0 == false)  //true
console.log(true == 1)  //true
console.log(true == "1") //true
console.log(true == 42)  //false

Fermati sulle righe centrali, perché sono quelle che in Java sarebbero impensabili:

  • "1" == 1 è true: la stringa "1" viene convertita nel numero 1, e 1 == 1.
  • 0 == false è true: false viene convertito nel numero 0.
  • true == 1 è true: true viene convertito nel numero 1.
  • true == "1" è true: doppia conversione — true → 1, e "1" → 1.
  • true == 42 è false: true diventa 1, e 1 != 42.

In Java, "1" == 1 non compilerebbe nemmeno (tipi incompatibili). In JavaScript è un'espressione legale che restituisce true. Il problema è che queste conversioni seguono regole complesse e poco intuitive, e affidarsi a == significa affidarsi a quelle regole.

⚠️ Regola pratica: usa sempre ===, mai ==. Non esiste un caso in cui == faccia quello che vuoi e === no — esistono solo casi in cui == fa qualcosa che non ti aspetti.

7.4 L'uguaglianza stretta (===)

L'operatore di uguaglianza stretta (===) verifica se i suoi due operandi sono uguali senza effettuare alcuna conversione di tipo. Se gli operandi sono di tipi diversi, il controllo restituisce immediatamente false, senza nemmeno guardare i valori.

console.log(42 === 42)   //true
console.log("JS" === "JS") //true
console.log("1" === 1)   //false
console.log(0 === false)  //false
console.log(true === 1)  //false
console.log(true === "1") //false
console.log(true === 42)  //false

Confronta questo blocco con quello precedente: gli stessi sette confronti, ma ora tutti i casi "strani" restituiscono false. "1" === 1 è false perché una stringa e un numero non sono mai lo stesso tipo. 0 === false è false per lo stesso motivo. Il comportamento è quello che ti aspetteresti: prevedibile, e senza sorprese.

Confronto affiancato:

Espressione == === Perché differiscono
42 vs 42 true true Stesso tipo, stesso valore
"JS" vs "JS" true true Stesso tipo, stesso valore
"1" vs 1 true false == converte la stringa in numero
0 vs false true false == converte false in 0
true vs 1 true false == converte true in 1
true vs "1" true false == converte entrambi
true vs 42 false false == converte, ma 1 != 42

Nota: l'operatore !== è semplicemente la negazione di ===, e vale la stessa raccomandazione: usa !==, non !=.

8. Control Flow

if, if-else, for, while, do, switch hanno la stessa sintassi e la stessa semantica di Java. Anche gli statement continue e break funzionano esattamente come in Java.

if(condition){
 //code
}

if(condition){
 //code
} else {
 //code
}

do {
 //code
} while(condition);

for(let i=0;i<10;i++){
 //code
}

Nota che nel for la variabile del contatore si dichiara con let: è il modo moderno e corretto, e sfrutta il block-level scope di cui abbiamo parlato — la variabile i esiste solo dentro il ciclo, esattamente come in Java.

Un'avvertenza per il futuro: in Java, la condizione di un if o di un while deve essere un boolean. In JavaScript questo vincolo non c'è: valori come 0, "", null, undefined e NaN sono considerati falsi (falsy), mentre tutto il resto è considerato vero (truthy). Quindi if ("ciao") è legale e la condizione risulta vera. Questo meccanismo è comodo ma insidioso, e ci torneremo quando servirà.

9. Funzioni

Arriviamo alla prima vera differenza strutturale rispetto a Java, e vale la pena affrontarla con calma perché condiziona tutto il resto della lezione (compresi gli oggetti).

In Java, i metodi vivono dentro una classe e appartengono a quella classe. Puoi assegnare un metodo a una variabile solo in forme limitate (lambda, method reference). In JavaScript le funzioni sono cittadini di prima classe: sono valori come i numeri e le stringhe, si assegnano a variabili, si passano come argomenti, si restituiscono da altre funzioni. Questa differenza è la radice di quasi tutto ciò che segue.

9.1 Dichiarare una funzione

La sintassi di base è questa:

function greet(name){
 console.log(`Hello ${name}`); //backticks for template literals
}
greet("Web Technologies"); //prints "Hello Web Technologies"

Confrontala con Java: function greet(name) { ... } corrisponde a void greet(String name) { ... }. Nota cosa manca: il tipo di ritorno (void) e il tipo del parametro (String). In JavaScript non si dichiarano, per la stessa ragione per cui non si dichiara il tipo delle variabili.

Lo scope di una dichiarazione di funzione è lo scope corrente in cui la dichiarazione avviene — ed è una cosa a cui torneremo tra poco, perché le funzioni, come le variabili, subiscono l'hoisting.

💡 Template Literals. Nel corpo della funzione compare `Hello ${name}` — non sono virgolette normali ma backtick (`), e il ${name} è un segnaposto. Questa sintassi si chiama template literal ed è l'equivalente JavaScript della concatenazione di stringhe Java: "Hello " + name diventa `Hello ${name}`. Il vantaggio è che puoi interpolare qualsiasi espressione, non solo una variabile.

Come digitare i backtick (utile, perché sulla tastiera italiana non sono ovvi):

  • Windows: ALT + 096 sul tastierino numerico
  • Mac OS: Option + 9
  • Linux: ALT Gr + '

9.2 Parametri con valore di default

In Java, se non passi un argomento a un metodo, ottieni un errore di compilazione (a meno di usare gli overload). In JavaScript no. Quando non vengono passati argomenti in una chiamata, i parametri corrispondenti sono inizializzati a undefined — e il programma va avanti tranquillamente.

Poiché questo è scomodo, JavaScript permette di specificare valori di default per i parametri:

function greet(name, message="Hello"){ //message has a default value
 console.log(`${message} ${name}`);
}
greet("Web Technologies");         // Hello Web Technologies
greet("Web Technologies", "Ciao"); // Ciao Web Technologies
greet();                           // Hello undefined

Leggiamo le tre chiamate:

  • La prima passa solo name, quindi message usa il default "Hello".
  • La seconda passa entrambi, e message diventa "Ciao".
  • La terza non passa nulla: message usa il default "Hello", ma name — che non ha default — resta undefined. Ecco perché l'output è "Hello undefined" invece di un errore.

Nota: questa sintassi sostituisce, in buona parte, gli overload di Java. In Java scriveresti due metodi greet(String) e greet(String, String) con lo stesso nome; in JavaScript scrivi una sola funzione con un valore di default.

9.3 L'hoisting delle funzioni

Torniamo all'hoisting, che avevamo visto sulle variabili. Si applica anche alle dichiarazioni di funzione, e in questo caso è ancora più evidente:

greet("Web Technologies"); //prints "Hello Web Technologies" (!)
function greet(name, message="Hello"){
 console.log(`${message} ${name}`);
}

Guarda l'ordine: la funzione viene chiamata alla prima riga, ma dichiarata alla terza. In Java questo non compilerebbe. In JavaScript funziona perfettamente, per la ragione che già conosci: il motore, prima di eseguire, scansiona lo scope e "tira su" le dichiarazioni di funzione. E a differenza di quanto accade con let/const, qui viene tirata su l'intera funzione, non solo il nome — quindi è immediatamente chiamabile.

Attenzione — è un'arma a doppio taglio. Il fatto che le funzioni si possano chiamare prima di essere dichiarate è comodo, ma è anche il motivo per cui l'ordine del codice smette di essere una guida affidabile per capire cosa succede. In Java potevi leggere un file dall'alto verso il basso e sapere sempre cosa era già stato definito. In JavaScript non più: devi ricordarti dell'hoisting.

9.4 Scope interno, visibilità e closure

Questa sottosezione introduce due concetti che vanno capiti bene, perché sono la base di tutto il resto.

  • Una funzione crea il proprio scope.
  • Le variabili (e le funzioni) dichiarate al suo interno non sono visibili negli scope esterni.
  • Una funzione può accedere alle variabili degli scope esterni (closure), purché non siano mascherate (masked) nel proprio scope.

I primi due punti ti sono familiari: sono le stesse regole di Java. Una variabile locale di un metodo non è visibile fuori da quel metodo.

Il terzo punto è quello nuovo, e si chiama closure: una funzione può leggere e usare le variabili dello scope in cui è stata definita, anche se quelle variabili non sono suoi parametri né sue locali.

let message = "Hello";
console.log(greet("Web Technologies")); //output: Hello Web Technologies!
function greet(name){         // hoisted to the beginning of the global scope
 return generateMessage();
 function generateMessage(){ // hoisted to the beginning of greet's scope
  return `${message} ${name}!`;
 }
}

Leggi questo esempio lentamente, perché ci sono due livelli di annidamento. La funzione greet riceve name come parametro e chiama generateMessage(). La funzione generateMessage non riceve nulla — non ha parametri — eppure nel suo return usa sia message (dallo scope globale) sia name (dai parametri di greet). Li vede entrambi perché è definita dentro greet, che a sua volta è definita nello scope globale.

Scope GLOBALE
├── message = "Hello"
└── greet()                    <-- hoisted qui
    └── Scope di greet()
        ├── name = "Web Technologies"   (parametro)
        └── generateMessage()           <-- hoisted qui
            └── Scope di generateMessage()
                accede a: name, message  (closure sugli scope esterni)

Questa è una catena di scope: ogni funzione può guardare verso l'esterno, mai verso l'interno. generateMessage vede name e message; greet non vedrebbe una variabile dichiarata dentro generateMessage.

Il rovescio della medaglia è la visibilità verso l'esterno: generateMessage è locale allo scope di greet, quindi non può essere referenziata da fuori:

let message = "Hello";
console.log(greet("Web Technologies")); //output: Hello Web Technologies!
function greet(name){
 return generateMessage();
 function generateMessage(){ // hoisted to the beginning of greet's scope
  return `${message} ${name}!`;
 }
}
generateMessage(); // Raises ReferenceError: generateMessage is not defined

L'ultima riga fallisce con ReferenceError: generateMessage is not defined. Il messaggio è chiaro: quella funzione non esiste fuori da greet. È lo stesso principio per cui in Java un metodo privato non è raggiungibile dall'esterno — solo che qui la restrizione è strutturale (lo scope), non dichiarativa (il modificatore private).

9.5 Function Expressions

Finora abbiamo visto funzioni dichiarate. Esiste però un secondo modo di crearle: le function expressions, in cui una funzione viene assegnata a una variabile.

// standard function expression
let greet = function(name) {
 console.log(`Hello ${name}!`);
}
greet("Web Technologies"); // output: Hello Web Technologies!

// alternative, using arrow functions
let greet = (name) => {
 console.log(`Hello ${name}!`);
}

Qui c'è un salto concettuale importante: la funzione a destra dell'= è un valore, esattamente come 42 o "ciao". La variabile greet non è "il nome della funzione": è una variabile che contiene una funzione. La differenza sembra sottile ma cambia tutto, ed è il motivo per cui JavaScript è detto linguaggio funzionale: le funzioni si possono passare in giro come qualsiasi altro dato.

La seconda forma è ancora più compatta. La sintassi (name) => { ... } si chiama arrow function, e in Java la conosci come lambda: (name) -> { ... }. È esattamente la stessa idea, con una freccia diversa. Le arrow function sono utilissime per le funzioni brevi, e più avanti (nella sezione sugli oggetti) scoprirai che hanno anche una particolarità importante riguardo a this.

⚠️ Attenzione: in questi casi si applicano le stesse regole dell'hoisting delle variabili! Questo è il punto cruciale, ed è il contenuto della prossima sottosezione.

9.6 Function Expressions e hoisting: la differenza che conta

Abbiamo due modi di creare funzioni che si comportano diversamente rispetto all'hoisting. Vale la pena fissare la distinzione con un esempio affiancato:

greet(); //ReferenceError: greet is not defined
{
  greet(); //output: Hello
  function greet(){
   console.log("Hello");
  }
}

salute(); //ReferenceError: salute is not defined
{
  salute(); //ReferenceError: uninitialized
  let salute = function(){
   console.log("Howdy");
  }
}

Analizziamo i quattro casi:

  1. greet() fuori dal blocco → ReferenceError: greet is not defined. La dichiarazione di funzione è hoisted all'inizio del suo scope, che è il blocco {} — non lo scope esterno.
  2. greet() dentro il blocco, prima della dichiarazione → funziona e stampa "Hello". Qui è tutta la dichiarazione di funzione a essere hoisted, quindi la funzione è già pronta.
  3. salute() fuori dal blocco → ReferenceError: salute is not defined. Stessa ragione del caso 1.
  4. salute() dentro il blocco, prima dell'assegnazione → ReferenceError: uninitialized. Qui la variabile salute è dichiarata con let, quindi subisce l'hoisting della sola dichiarazione e si trova nella sua TDZ. La funzione non è ancora stata assegnata, quindi non è chiamabile.

La regola, in una tabella:

Tipo Cosa viene hoisted Chiamabile prima della dichiarazione?
Function declaration
function greet(){}		 Tutta la funzione ✅ Sì (nello stesso scope)
Function expression
let greet = function(){}		 Solo la variabile (TDZ) ❌ No (ReferenceError)

Se hai capito la differenza tra hoisting di let e hoisting di function, hai capito entrambi gli argomenti — sono lo stesso meccanismo applicato a due cose diverse.

9.7 Funzioni annidate e closure

L'ultimo tassello sulle funzioni. Una funzione è detta nested (annidata) quando è creata dentro un'altra funzione. Abbiamo già visto un esempio nella sezione sullo scope, ma qui ne vediamo la conseguenza più interessante:

  • Le funzioni annidate possono essere restituite e usate all'esterno della funzione originale.
  • Indipendentemente da dove vengono usate, le funzioni annidate possono accedere al contesto esterno della funzione che le ha create.
function getGreeter(message) {
 let sep = ",";
 return function(name) {
  console.log(`${message}${sep} ${name}!`);
 }
}
let helloGreeter = getGreeter("Hello");
helloGreeter("Web"); //Hello, Web!
let howdyGreeter = getGreeter("Howdy");
howdyGreeter("JS"); //Howdy, JS!

Questo esempio merita di essere letto con attenzione, perché fa una cosa che in Java non è possibile fare allo stesso modo.

Osserva getGreeter: prende message, dichiara una variabile locale sep, e restituisce una funzione — non un valore, non un oggetto, ma una funzione. Ora guarda la prima chiamata: getGreeter("Hello") viene eseguita, e al momento del return la sua esecuzione è finita. In Java, a questo punto, le variabili locali message e sep non esisterebbero più.

E invece:

getGreeter("Hello")  ──>  crea un contesto con { message: "Hello", sep: "," }
                                        │
                                        └──> restituisce function(name){...}
                                             che "ricorda" message e sep
                                             anche dopo che getGreeter è terminata

La funzione restituita si porta dietro message e sep. Quando la chiami con helloGreeter("Web"), lei usa il suo message ("Hello") e il suo sep (","), producendo "Hello, Web!".

E il bello è che ogni chiamata a getGreeter crea un contesto separato: howdyGreeter ha il suo message ("Howdy") e non è influenzato da helloGreeter. Sono due funzioni indipendenti che hanno "catturato" due contesti diversi.

Questo meccanismo si chiama closure: una funzione cattura le variabili dello scope in cui è stata definita e le mantiene in vita finché la funzione stessa esiste. È il concetto più potente della lezione, ed è ciò che rende possibile molta della programmazione JavaScript moderna.

10. Oggetti

Siamo all'ultima e più corposa sezione. Se le funzioni rappresentavano la prima differenza strutturale con Java, gli oggetti rappresentano la seconda — e per certi versi la più radicale.

In Java, per avere un oggetto devi prima definire una classe. La classe è il progetto, l'oggetto è l'istanza. Non esiste un oggetto senza una classe.

In JavaScript questo vincolo non c'è. Un oggetto si crea direttamente, scrivendolo, senza passare da una classe. La classe (come vedremo nella sottosezione sui costruttori) diventa una convenzione per generare oggetti simili, non un requisito per crearne uno.

10.1 Creare un oggetto

  • Gli oggetti sono contenitori di dati key:value.
  • Possiamo aggiungere proprietà a un oggetto nel momento in cui lo creiamo.
  • Una proprietà ha una key (chiave, a.k.a. nome o identificatore) prima dei : e un value (valore) alla sua destra. Le dichiarazioni di proprietà sono separate da virgole.
let a = new Object(); // "object constructor" syntax
let b = {};           // "object literal" syntax, used more often
let pet = {
 name: "Hannibal",   // by key "name" store value "Hannibal"
 age: 7              // by key "age"  store value 7
}

Le prime due righe mostrano le due sintassi possibili. La prima, new Object(), è quella che ricorda più Java, ma è rara; la seconda, {} (le graffe vuote), si chiama object literal ed è quella che userai sempre.

L'oggetto pet è il caso interessante. Guarda cosa contiene: la key name con valore "Hannibal", e la key age con valore 7. Nota che non c'è nessuna classe dietro. In Java, per ottenere un oggetto con name e age dovresti scrivere:

class Pet {
    String name;
    int age;
}
Pet pet = new Pet();
pet.name = "Hannibal";
pet.age = 7;

In JavaScript tutte quelle righe si riducono a let pet = { name: "Hannibal", age: 7 }. La classe Pet semplicemente non serve.

Da tenere a mente: le property key sono stringhe. Nella forma più comune (come name e age) si scrivono senza virgolette, ma il linguaggio le tratta come stringhe — e questo spiega perché, più avanti, potrai accedervi anche con la notazione a parentesi quadre.

10.2 Accedere alle proprietà

Per leggere una proprietà si usa la dot notation, cioè il punto:

let pet = {
 name: "Hannibal",
 age: 7
}
console.log(pet.name);     // output: Hannibal
console.log(pet.age);      // output: 7
console.log(pet.nickname); // output: undefined

Le prime due righe ti sono familiari: pet.name è quello che in Java avresti scritto per accedere a un campo pubblico.

La terza riga è invece una differenza importante: pet.nickname accede a una proprietà che non esiste. In Java, pet.nickname dove nickname non è un campo dichiarato sarebbe un errore di compilazione. In JavaScript non è un errore: restituisce undefined.

⚠️ Ricorda questa cosa, perché è una delle fonti di bug più frequenti. Un errore di battitura in un nome di proprietà non ti dà nessun avviso: ottieni semplicemente undefined, e il programma continua. Se poi provi a usare quel valore come se fosse valido, l'errore emergerà molto più tardi e molto lontano dalla vera causa.

10.3 Aggiungere e cancellare proprietà

Ecco un'altra cosa che in Java non si può fare. In Java, la struttura di un oggetto è fissata dalla classe: se Pet ha due campi, un oggetto Pet avrà quei due campi e basta. Puoi aggiungerne un terzo solo modificando la classe e ricompilando.

In JavaScript, un oggetto è un contenitore aperto: puoi aggiungere e togliere proprietà mentre il programma gira.

let pet = {
 name: "Hannibal",
 age: 7
}
pet.nickname = "the Affable"; // new property
delete pet.age;               // delete property
console.log(pet.name);        // "Hannibal"
console.log(pet.age);        // undefined
console.log(pet.nickname);    // "the Affable"
console.log(pet);   // print object in console
console.table(pet); // alternative way to print objects in console

Due operazioni nuove:

  • Aggiungere una proprietà è banale: basta assegnarle un valore (pet.nickname = "the Affable"). Non serve averla dichiarata prima — se non esiste, viene creata.
  • Cancellare una proprietà si fa con la keyword delete (delete pet.age). Da quel momento pet.age vale undefined, esattamente come se non fosse mai esistita.

Da notare anche il console.table(pet) finale: è un'utilità della console del browser che stampa l'oggetto in formato tabellare, molto più leggibile del console.log normale quando l'oggetto ha diverse proprietà. È il tuo strumento principale per ispezionare gli oggetti mentre sviluppi.

10.4 La square bracket notation

Le key delle proprietà possono anche contenere spazi, cosa che in Java non sarebbe possibile perché lì gli identificatori non ammettono spazi. Per accedere a queste proprietà non puoi usare la dot notation, e serve una notazione alternativa:

let dog = {
 name: "Sif",
 "is a good boy": true
}
console.log(dog["name"]);
console.log(dog["is a good boy"]);
//expressions can be used as keys
dog["is the "+"best boy"] = true;
console.table(dog);

La square bracket notation consiste nello scrivere la key tra parentesi quadre, tra virgolette (perché come detto le key sono stringhe). Le prime due righe sono il caso base: dog["name"] è equivalente a dog.name, mentre dog["is a good boy"] è l'unico modo possibile per accedere a una key con spazi.

La terza riga mostra la vera potenza della notazione. Dentro le parentesi quadre puoi mettere un'espressione, non solo una stringa letterale:

dog["is the "+"best boy"] = true;

Qui l'espressione "is the " + "best boy" viene valutata a runtime, produce la stringa "is the best boy", e quella stringa diventa la key della nuova proprietà. Questo significa che la key di una proprietà può essere calcolata dinamicamente — per esempio in base a un input dell'utente, o al contenuto di un'altra variabile. È il genere di flessibilità per cui in Java servirebbero le Map, mentre qui è parte del linguaggio.

Regola pratica: usa la dot notation quando la key è fissa e la conosci mentre scrivi (pet.name). Usa la square bracket notation quando la key è dinamica, contiene caratteri speciali, o è il risultato di un'espressione.

10.5 Le variabili contengono riferimenti

Qui arriva un concetto che in Java conosci già bene, ma che è utile rivedere perché in JavaScript si presenta in una forma leggermente diversa.

let firstPet = {
 name: "Richard",
 species: "Lizard"
}
let secondPet = firstPet;
secondPet.name = "Chuck";
secondPet.species = "Duck";
console.log(firstPet);  // Object { name: "Chuck", species: "Duck" }
console.log(secondPet); // Object { name: "Chuck", species: "Duck" }
console.log(firstPet == secondPet);  // true, same value
console.log(firstPet === secondPet); // true (both are references, same value)

La riga chiave è let secondPet = firstPet;. Ti aspetteresti che questa crei una copia dell'oggetto. In realtà non copia nulla: assegna a secondPet lo stesso riferimento che ha firstPet.

firstPet  ──────┐
                ├──────>  { name: "Chuck", species: "Duck" }
secondPet ──────┘
           (entrambe puntano allo STESSO oggetto in memoria)

Le conseguenze sono visibili nell'output: dopo secondPet.name = "Chuck", anche firstPet.name è "Chuck", perché entrambe le variabili puntano allo stesso oggetto in memoria. Modificare tramite una variabile modifica ciò che vede l'altra.

Questo comportamento è identico a Java, dove una variabile di tipo oggetto contiene un riferimento e l'assegnazione secondPet = firstPet copia il riferimento, non l'oggetto. Se hai già interiorizzato questo in Java, hai già capito anche qui.

Le ultime due righe, invece, aggiungono una sfumatura: sia firstPet == secondPet sia firstPet === secondPet restituiscono true. Confrontando due riferimenti allo stesso oggetto, i due operatori concordano — perché i tipi sono uguali e il valore (la referenza) è lo stesso. Le differenze tra == e === che abbiamo visto nella sezione 7 emergono quando i tipi sono diversi.

10.6 Clonare un oggetto

Se l'assegnazione non copia, come si fa una copia vera? Bisogna iterare su ogni proprietà e copiarle una per una:

let pet = {
 name: "Richard", species: "Lizard"
}
let copy = clone(pet);
copy.name = "Chuck";
console.log(pet.name); // Richard
console.log(copy.name); // Chuck

function clone(object){
 let copy = {}; // new object
 for(let key in object){
  copy[key] = object[key];
 }
 return copy;
}

Vediamo come funziona la funzione clone. Crea un oggetto nuovo e vuoto (let copy = {}), poi usa un ciclo for...in per scorrere tutte le key dell'oggetto originale. Per ciascuna, copia il valore nel nuovo oggetto. Alla fine restituisce la copia.

Una sola cosa da notare nella sintassi: for(let key in object) è una forma di ciclo che non hai visto in Java. Il for...in scorre le key di un oggetto (una per iterazione), e in ogni iterazione key contiene il nome della proprietà corrente. È il modo standard per attraversare un oggetto.

Il risultato è quello che volevamo: ora modificare copy.name non tocca pet.name. I due oggetti sono indipendenti, perché sono due oggetti distinti in memoria.

Nota: la funzione clone che abbiamo scritto è nostra, non è una funzione di JavaScript. L'abbiamo implementata a mano per capire il meccanismo — e tra due sottosezioni vedremo che il linguaggio ne offre già di pronte.

10.7 Shallow vs Deep Cloning

La funzione clone che abbiamo appena scritto ha un limite, ed è un limite che vale la pena capire bene perché è una trappola classica.

Il valore di una proprietà di un oggetto può essere a sua volta un oggetto. Nel prossimo esempio, pet ha una proprietà owner che è un oggetto con name e age:

let pet = {
 name: "Garfield", species: "Cat",
 owner: {
  name: "John", age: 17
 }
}
let copy = clone(pet);
copy.owner.name = "Liz";
console.log(pet.owner.name); // Liz
console.log(copy.owner.name); // Liz

Cosa è successo? Abbiamo modificato copy.owner.name, ma anche pet.owner.name è cambiato. Il clone non era completo.

Il motivo è che la funzione clone copia i valori delle proprietà uno per uno. Per le proprietà con valori semplici (name, species) va bene. Ma owner non è un valore semplice: è un oggetto, quindi il suo valore è un riferimento. Quindi copy.owner e pet.owner finiscono per puntare allo stesso oggetto interno — esattamente lo stesso fenomeno della sottosezione 10.5, solo un livello più in profondità.

Questo tipo di copia si chiama shallow clone (copia superficiale): copia il primo livello dell'oggetto, ma gli oggetti interni restano condivisi.

SHALLOW CLONE                          DEEP CLONE
pet ──> { name, species,               pet ──> { name, species,
          owner ──┐                              owner ──> { name, age }  (copia)
        }         │                      copy ─> { name, species,
copy ─> { name, species,                           owner ──> { name, age }  (copia)
          owner ──┘  (STESSA referenza)         }
        }

Per ottenere un deep clone — che cloni anche gli oggetti interni, ricorsivamente — bisogna usare la ricorsione: quando la proprietà è a sua volta un oggetto, invece di copiarla, la si clona con una chiamata ricorsiva a clone:

// deep clone
function clone(object){
 let copy = {};
 for(let key in object){
  if(typeof object[key] === "object"){
   copy[key] = clone(object[key]);
  }
  else {
   copy[key] = object[key];
  }
 }
 return copy;
}

La differenza rispetto alla versione precedente è tutta nell'if: se typeof object[key] è "object", la proprietà è un oggetto, quindi si chiama clone su di essa (ricorsione), invece di copiarne il riferimento. Altrimenti è un valore semplice, e lo si copia direttamente.

Nota importante — non serve reinventare la ruota. Implementare i metodi di clone da zero ha valore didattico (ora sai cosa succede sotto il cofano, e sai perché il clone profondo richiede la ricorsione), ma nel codice reale non devi implementarli ogni volta. JavaScript offre alternative già pronte:

  • Object.assign() → shallow clone
  • structuredClone() → deep clone

Sapere quale delle due usare è esattamente la distinzione che hai appena imparato.

Riepilogo:

Tipo di copia Cosa copia Cosa condividono i due oggetti Strumento
Shallow Solo il primo livello Gli oggetti interni (per riferimento) Object.assign() o ciclo semplice
Deep Tutti i livelli, ricorsivamente Nulla — completamente indipendenti structuredClone() o ricorsione

10.8 Metodi

Torniamo per un momento alle funzioni. Abbiamo detto che le funzioni sono valori come gli altri — quindi possono anche essere il valore di una proprietà. Quando una proprietà di un oggetto è una funzione, si chiama metodo.

Il concetto ti è familiare: in Java, i metodi di una classe sono esattamente questo. Le seguenti sono tutte modalità equivalenti di definire metodi:

let p = {
 name: "John",
 greet: function(){
  console.log("Hi!");
 }
}
p.greet(); // Hi!

let p = {
 name: "John"
}
p.greet = function(){
 console.log("Hi!");
}

let p = {
 name: "John",
  greet: greet
}
function greet(){
 console.log("Hi!");
}

Vale la pena commentare la differenza tra le tre:

  • La prima definisce il metodo direttamente dentro l'object literal, come una proprietà il cui valore è una funzione.
  • La seconda parte da un oggetto senza il metodo e lo aggiunge dopo, con la stessa sintassi con cui aggiungeresti una proprietà qualsiasi. È la dimostrazione pratica che gli oggetti sono contenitori aperti.
  • La terza è la più interessante: dichiara la funzione greet fuori dall'oggetto, e poi assegna la funzione stessa come valore della proprietà greet. Questo è possibile solo perché le funzioni sono valori — in Java non potresti mai fare una cosa del genere con un metodo.

In tutti e tre i casi, la chiamata è la stessa: p.greet(), che stampa "Hi!".

10.9 Method Shorthand

Esiste anche una sintassi abbreviata per dichiarare metodi dentro un object literal:

// classic version
let p = {
 name: "John",
 sayHi: function(){
  console.log("Hi!");
 }
}
p.sayHi(); // Hi!

// shorthand version
let p = {
 name: "John",
 sayHi(){
  console.log("Hi!");
 }
}

La differenza è puramente sintattica: nella versione classica scrivi sayHi: function(){ ... }, nella versione abbreviata scrivi sayHi(){ ... } — hai tolto i due punti e la parola function. Il risultato è identico.

La forma abbreviata è quella preferita nel codice moderno, perché è più pulita e perché è la forma che assomiglia di più a Java. Vedrai che negli esempi successivi (nella sottosezione su this) verrà usata proprio questa.

10.10 La keyword this

Arriviamo a un concetto che conosci da Java ma che in JavaScript funziona in modo profondamente diverso. È probabilmente la cosa più importante di tutta questa sezione.

Il punto di partenza è comune: è normale che un metodo di un oggetto abbia bisogno di accedere ad altre proprietà dello stesso oggetto. In Java lo fai con this.name. In JavaScript esiste la stessa keyword:

let john = {
 name: "John",
 greet(){
  console.log(`Hi, I'm ${this.name}!`);
 }
}
john.greet(); // Hi, I'm John!

Fin qui tutto familiare: this.name dentro il metodo greet accede alla proprietà name dell'oggetto john, e l'output è "Hi, I'm John!". Se ti fermassi qui, penseresti che this funzioni come in Java.

Ma ecco il punto:

In Java, this è deciso a compile-time: è sempre l'istanza della classe su cui il metodo è stato chiamato, e il compilatore sa esattamente quale sia. In JavaScript, il valore di this viene valutato a runtime, in base al contesto — cioè in base a come la funzione viene chiamata.

let john = {name: "John"};
let will = {name: "Will"};
let greet = function(){
 console.log(`Hi, I'm ${this.name}!`);
}
// same function is assigned as a method to two objects
john.greet = greet;
will.greet = greet;
john.greet(); // Hi, I'm John!
will.greet(); // Hi, I'm Will!

Guarda attentamente cosa succede qui, perché è il cuore della questione:

  1. greet è una funzione standalone che usa this.name — ma in quel momento this non è legato a nulla.
  2. La stessa identica funzione viene assegnata come metodo a due oggetti diversi: john.greet = greet e will.greet = greet.
  3. Chiamando john.greet(), this è john → output "Hi, I'm John!".
  4. Chiamando will.greet(), this è will → output "Hi, I'm Will!".

La stessa funzione produce due risultati diversi. Questo in Java sarebbe impensabile: un metodo appartiene a una classe, e this è sempre l'istanza di quella classe. Qui la funzione non "appartiene" a nessuno: è un valore che hai messo in due posti diversi, e this assume il valore dell'oggetto su cui il metodo viene invocato (la parte prima del punto).

La regola, in breve: questoOggetto.nomeMetodo() → dentro nomeMetodo, this vale questoOggetto. Il valore di this dipende dalla chiamata, non dalla definizione.

10.11 Arrow function come metodi: la trappola di this

C'è una conseguenza importante di quanto appena detto, e riguarda le arrow function che avevamo visto nella sezione 9.5.

  • Le arrow function non hanno this.
  • Se this viene referenziato dentro una arrow function, viene preso dal contesto esterno (outer context), non dall'oggetto su cui la funzione viene chiamata.
let john = {nick: "John"};
let will = {nick: "Will"};
let greet = () => {
 console.log(`Hi, I'm ${this.nick}!`);
}
john.greet = greet;
will.greet = greet;
john.greet(); // Hi, I'm undefined!
will.greet(); // Hi, I'm undefined!

Confronta questo esempio con quello della sottosezione precedente: è lo stesso codice, con una sola differenza — greet è definita come arrow function (() => {...}) invece che come function() {...}.

E il risultato cambia completamente:

  • Con function(), john.greet() stampava "Hi, I'm John!".
  • Con () =>, john.greet() stampa "Hi, I'm undefined!".

Il motivo è che l'arrow function ignora l'oggetto su cui viene chiamata. Non avendo un this proprio, prende quello dello scope in cui è stata definita — che nel nostro caso è lo scope globale, dove nick non esiste. Quindi this.nick è undefined.

⚠️ Regola pratica, e vale la pena memorizzarla:

  • Se stai definendo un metodo di un oggetto che ha bisogno di accedere alle proprietà dell'oggetto, usa function() o la method shorthand (come greet(){}). Non usare le arrow function.
  • Se stai definendo una funzione normale che non ha bisogno di this, le arrow function sono più concise e vanno benissimo.

Ricorda che in Java non hai mai dovuto fare questa distinzione: qui è una scelta che può rompere silenziosamente il codice.

10.12 Costruttori

Torniamo al problema lasciato in sospeso all'inizio della sezione: abbiamo detto che in JavaScript la classe non è necessaria per creare un oggetto. Ma se devo creare molti oggetti simili, scrivere l'object literal ogni volta è scomodo e ripetitivo. In Java questo problema lo risolvevi con una classe e un costruttore.

In JavaScript si fa con le constructor functions e la keyword new.

I costruttori sono normali funzioni. Si applicano però due convenzioni:

  1. Il loro nome dovrebbe iniziare con la lettera maiuscola.
  2. Dovrebbero essere invocati solo usando la keyword new.

La prima convenzione esiste perché, come sappiamo, JavaScript non ha modo di distinguere una funzione normale da un costruttore guardandone la sintassi. La maiuscola è un segnale per chi legge il codice (e per gli strumenti di sviluppo), non per il motore. La seconda è più sostanziale, ed è spiegata dalla meccanica che segue.

Quando una funzione viene eseguita con new:

  1. Viene creato un nuovo oggetto vuoto e assegnato a this.
  2. Il corpo della funzione viene eseguito. Tipicamente modifica this.
  3. Il valore di this viene restituito.
function Pet(name, species){
 this.name  = name;
 this.species = species;
 this.age   = undefined;
}
let rick = new Pet("Richard", "Lizard");
let chuck = new Pet("Chuck", "Duck");

Questo è il momento in cui il comportamento dinamico di this torna utile, e l'analogia con Java diventa stretta. In Java, dentro un costruttore, this è l'oggetto appena creato. Qui funziona allo stesso modo, ma solo perché hai usato new: la keyword new è ciò che crea l'oggetto vuoto e lo lega a this prima che il corpo venga eseguito.

Il risultato è che rick è un oggetto con name: "Richard", species: "Lizard" e age: undefined; chuck è un oggetto analogo con i propri valori. Due oggetti indipendenti, generati dallo stesso "stampo".

💡 Perché la seconda convenzione è importante: chiamare Pet("Richard", "Lizard") senza new non dà errore. Il problema è che, non essendoci il passo 1, this non sarebbe il nuovo oggetto ma qualcos'altro (lo scope globale in modalità normale), e il costruttore finirebbe per sporcare variabili globali con name, species, age. Il codice sembrerebbe funzionare ma produrrebbe un oggetto undefined. Ecco perché la convenzione dice: un costruttore si invoca sempre e solo con new.

10.13 Optional Chaining: navigare proprietà che potrebbero non esistere

Ricordi l'avvertimento della sottosezione 10.2, quando pet.nickname — una proprietà inesistente — restituiva undefined senza dare errore? Quella permissività ha un rovescio della medaglia, ed è quello che vediamo ora.

let pet = {
 name: "Garfield"
}
console.log(pet.species); // undefined
console.log(pet.owner.name); //throws ReferenceError

La prima riga è il caso che conosciamo: pet.species non esiste, e otteniamo undefined.

La seconda riga è il problema. Stiamo cercando di accedere a pet.owner.name, ma pet.owner non esiste — quindi vale undefined. A quel punto stiamo chiedendo la proprietà name di undefined, e questo è impossibile: il codice lancia un ReferenceError.

In Java, questo scenario è il famigerato NullPointerException, e chi ha scritto codice Java sa quanto sia fastidioso. JavaScript ha lo stesso problema con un nome diverso, ed è comune quando si lavora con dati che arrivano dall'esterno (per esempio da un'API), dove non sai mai se una proprietà annidata esiste davvero.

In molti casi pratici potremmo preferire ottenere undefined — per esempio significherebbe "non c'è un proprietario conosciuto" — piuttosto che far crashare il programma.

Il modo ingenuo è verificare esplicitamente che la proprietà sia definita prima di accedere alle sue proprietà interne:

let ownerName = pet.owner ? pet.owner.name : undefined;

Qui usiamo l'operatore ternario: se pet.owner esiste, prendiamo pet.owner.name; altrimenti mettiamo undefined. Funziona — ma nota quanto sia ripetitivo e inelegante: per ogni livello di annidamento servirebbe un altro controllo, e con tre o quattro livelli il codice diventa illeggibile.

JavaScript offre un operatore dedicato per questo, ed è il ?.:

let ownerName = pet.owner?.name;

L'operatore di optional chaining ?. fa esattamente la stessa cosa della riga precedente, ma in modo compatto. Il suo comportamento è questo: se la parte sinistra è undefined (o null), interrompe immediatamente la valutazione — questo si chiama short-circuit — e restituisce undefined, senza nemmeno provare ad accedere alla proprietà a destra.

Quindi pet.owner?.name: se pet.owner esiste, restituisce il suo name; se pet.owner è undefined, si ferma e restituisce undefined — senza lanciare l'errore.

💡 Da ricordare: questo è il tuo strumento per gestire in modo pulito la stessa situazione che in Java ti dava la NullPointerException. Ogni volta che accedi a una proprietà annidata che potrebbe non esistere, chiediti se non sia il caso di usare ?..

10.14 Optional chaining: le varianti

L'optional chaining non serve solo ad accedere a proprietà annidate. Ha altre due forme:

let john = {
 name: "John",
 greet(){ return "Hi!"; },
 address: { "street name": "Web Dev Blvd" }
}
let mike = { name: "Mike", age: 17 }
console.log( john.greet?.() ); // Hi!
console.log( mike.greet?.() ); // undefined
console.log( john.address?.['street name']); // Web Dev Blvd
console.log( mike.address?.['street name']); // undefined

Guarda le differenze tra john (che ha il metodo greet e la proprietà address) e mike (che non ha né l'uno né l'altra).

Prima variante — chiamare un metodo che potrebbe non esistere. john.greet?.() restituisce "Hi!" perché greet esiste. mike.greet?.() restituisce undefined invece di dare errore: il ?. prima delle parentesi ferma la chiamata se il metodo non esiste. Senza il ?., mike.greet() lancerebbe un errore perché mike.greet è undefined e non si può invocare undefined.

Seconda variante — accesso con parentesi quadre. john.address?.['street name'] combina l'optional chaining con la square bracket notation che abbiamo visto nella sottosezione 10.4. Il ?. va messo prima delle parentesi quadre, e serve a proteggere l'accesso nel caso address non esista. Anche qui, mike non ha address, quindi otteniamo undefined invece di un errore.

Riepilogo delle forme:

Forma Uso Esempio
obj.prop?.nome Accesso a una proprietà annidata pet.owner?.name
obj.method?.() Chiamata a un metodo che potrebbe non esistere mike.greet?.()
obj?.['key'] Accesso con square bracket notation mike.address?.['street name']

10.15 Configurare le proprietà: i flag

Finora abbiamo trattato le proprietà come semplici coppie key:value. In realtà ogni proprietà ha, oltre al valore, tre attributi speciali (chiamati flag) che ne controllano il comportamento:

  • writable: se true, il valore può essere cambiato. Altrimenti la proprietà è read-only.
  • enumerable: se true, la proprietà viene elencata nei loop (come il for...in che abbiamo usato in clone).
  • configurable: se true, la proprietà può essere cancellata e i suoi flag modificati.

Quando creiamo una proprietà nel modo "tradizionale" — cioè scrivendola in un object literal o assegnandola con pet.nuova = ... — tutti i flag sono impostati a true. Ecco perché, fino ad ora, potevamo modificare, cancellare e iterare su tutto senza problemi: i permessi erano tutti concessi.

Questo concetto in Java non ha un equivalente diretto. Ci si avvicina l'idea dei modificatori di accesso (private, final), ma con una differenza sostanziale: mentre in Java i modificatori sono decisi una volta per tutte dalla classe, qui i flag si possono decidere proprietà per proprietà, a runtime.

10.16 Object.defineProperty()

Per creare una proprietà specificando i suoi flag si usa Object.defineProperty():

let pet = { species: "cat" }
Object.defineProperty(pet, "name", {
 value: "Garfield",
 writable: false,
 enumerable: false,
 configurable: false
})
for(let key in pet){
 console.log(`Key: ${key}`); //only prints Key: species
}
pet.name = "Odie";  //TypeError: "name" is read-only
delete pet.species; //works
delete pet.name;    //TypeError: property "name" is non-configurable

⚠️ Attenzione, ed è una differenza importante: quando le proprietà vengono create con Object.defineProperty() e non specifichi un flag, quel flag ha valore di default false. È l'opposto del modo tradizionale! Quindi, se scrivessi Object.defineProperty(pet, "name", { value: "Garfield" }) senza elencare i flag, otterresti una proprietà read-only, non enumerabile e non configurabile — probabilmente non quello che volevi.

Vediamo gli effetti dei tre flag false nell'esempio:

Operazione Risultato Flag responsabile
for...in su pet stampa solo species enumerable: false — name viene nascosta al ciclo
pet.name = "Odie" TypeError writable: false — la proprietà è read-only
delete pet.species funziona species è stata creata nel modo tradizionale, quindi è configurabile
delete pet.name TypeError configurable: false

Nota il contrasto tra le ultime due righe: delete pet.species funziona (perché species è una proprietà normale, con tutti i flag a true), mentre delete pet.name fallisce (perché name è stata creata con configurable: false). Sono nello stesso oggetto, ma si comportano diversamente — perché i flag sono per proprietà, non per oggetto.

10.17 Property Getters e Setters

Concludiamo con un concetto che ti farà sentire a casa, perché è la versione JavaScript di qualcosa che conosci bene.

Esistono due tipi di proprietà di un oggetto:

  • Data properties: memorizzano un valore — sono tutte quelle viste finora.
  • Accessor properties: sono funzioni che vengono eseguite nel momento in cui la proprietà viene acceduta, sia in lettura sia in scrittura.

Le accessor properties sono rappresentate da due funzioni:

  • un getter, invocato quando la proprietà viene letta;
  • un setter, invocato quando la proprietà viene assegnata.

Le keyword get e set si usano per definirli dentro un object literal:

let p = {
 first: "John",
 last: "Smith",
 get fullName(){
  return `${this.first} ${this.last}`;
 },
 set fullName(name) {
  [this.first, this.last] = name.split(" "); // fancy destructuring assignment
 }
}
// notice that we access fullName as a property and not as a function (no "()")!
// from the outside, there is no difference between data and accessor properties
console.log(p.fullName); //John Smith
p.fullName = "Jane White";
console.log(p.fullName); //Jane White
p.fullName(); //TypeError: p.fullName is not a function

Questo esempio è ricco, quindi analizziamolo con calma.

L'oggetto p ha due proprietà normali, first e last, e una terza, fullName, definita una sola volta come getter e setter. Il getter restituisce la concatenazione di first e last: ogni volta che leggi p.fullName, la funzione viene eseguita e ti restituisce "John Smith". Il setter fa l'operazione inversa: quando assegni p.fullName = "Jane White", la stringa viene divisa sullo spazio e le due parti vengono assegnate a first e last.

Nota: [this.first, this.last] = name.split(" ") è un esempio di destructuring assignment, una sintassi compatta che permette di assegnare più variabili a partire da un array in una sola riga. name.split(" ") produce un array di due elementi (["Jane", "White"]), e il destructuring li assegna in ordine al primo e al secondo elemento. Lo incontrerai spesso in JavaScript.

Il dettaglio più importante è però come si usa fullName, ed è quello che la slide sottolinea con enfasi:

  • Si accede a fullName come a una proprietà, non come a una funzione: p.fullName, non p.fullName().
  • Dall'esterno non c'è alcuna differenza tra una data property e una accessor property. Chi usa l'oggetto scrive p.fullName e non sa (né deve sapere) che dietro c'è una funzione in esecuzione.
  • L'ultima riga lo dimostra: p.fullName() dà TypeError: p.fullName is not a function, perché fullName non è una funzione da chiamare — è una proprietà da leggere.

Il parallelo con Java è immediato: in Java hai i metodi getFullName() e setFullName(). In JavaScript, la stessa idea, ma con una differenza di forma: in Java chi usa la classe deve chiamare esplicitamente i metodi con le parentesi, mentre in JavaScript l'accesso è trasparente — si legge e si scrive come se fosse un campo normale. Il getter/setter resta invisibile a chi consuma l'oggetto, che è poi il senso dell'incapsulamento: decidi tu cosa succede quando qualcuno legge o scrive quella proprietà, senza che lui debba saperlo.
